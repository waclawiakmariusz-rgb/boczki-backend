## 2. Migracja v2 — jak działa i czego NIE robi

- **Nie uruchamia się przy starcie serwera.** Start wykonuje tylko `sprawdzSchematV2()` (odczyt `INFORMATION_SCHEMA` 4,5 s po starcie, zapis stanu `v2:<element>` do `Term_Migracje` — 51 pozycji; siedem wcześniejszych wpisów v1 pozostaje bez zmian). Brak elementów = `schemat_v2.gotowy=false` → ewidencja niedostępna (`code: SCHEMAT_V2`), rdzeń i kalendarz działają.
- **Uruchomienie jawne:** `node narzedzia/terminarz-zakupy-migracja.js` (cel: `.env.test`; `--dry-run`; odmowa, gdy host+baza są te same co w `.env`, chyba że `--env .env --wspolna-baza --potwierdzam` — decyzja właściciela). Pod `GET_LOCK('trm:migracja')`.
- **Ścieżka „pusty model”:** przed DDL liczy `Term_Zakupy`, `Term_Zakupy_Skladniki`, `Term_Zakupy_Ruchy`, `Term_Oferty` i `Term_Pozycje.zakup_skladnik_id IS NOT NULL`. Dane > 0 bez tabel v2 → **zatrzymanie i raport** (potrzebne przeniesienie historii — ZK-03). Zero `DROP/DELETE/TRUNCATE`. 51 kroków `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE … ADD COLUMN` (ER_DUP_FIELDNAME = „już było”), powtarzalnych.
- **Kompatybilność:** stare tabele/kolumny zostają (NULL-owalne, nieczytane przez v2 poza `Term_Pozycje.zakup_skladnik_id`, które v2 utrzymuje jako alias pierwszego aktywnego przydziału dla odczytów). Kod sprzed ZK-02 uruchomiony na bazie po migracji: nie czyta nowych tabel; **nie wolno go używać do mutacji wizyt z przydziałami** (zgodnie z §22.2 spec — powrót tylko do wersji znającej przydziały; przed pojawieniem się realizacji powrót kodu jest bezpieczny, bo tabele v2 są puste).
- **Odwracalność bez kasowania historii:** rollback kodu nie wymaga zmian schematu; dane v2 pozostają.
